# templates/

Templates for [cargo-generate], built around a **trunk + branches** model for
systematic firmware: one device runs many subsystems concurrently on a single
core (Embassy async tasks).

- **Trunk** — the per-board project template. Brings up the HAL, builds the
  shared `Trunk`, and starts every branch. Stays small.
- **Branch** — a subsystem module scaffolded by `bonsai branch <name>`,
  wired into the trunk automatically. Branches are MCU-portable.

## Layout

```
templates/
  _branch/
    branch.rs              # the branch scaffolds (consumer; branch_producer,
    branch_producer.rs     # branch_duplex, branch_roots) — baked into the
    branch_duplex.rs       # binary via include_str! so `bonsai branch` works
    branch_roots.rs        # anywhere. `{{branch_name}}` is a plain .replace,
                           # not Liquid.
    roots.rs               # the bridge every root shares; written to a tree's
                           # src/roots.rs by its first `branch --roots`.
  <mcu>/
    <board>/               # a trunk project (cargo-generate template)
      cargo-generate.toml
      pre.rhai             # derives target/probe vars from chip
      Cargo.toml
      .cargo/config.toml
      bonsai.toml          # per-nutrient path shape + capacity (read by the CLI)
      src/
        main.rs            # trunk: HW init, starts the pulse, then branches
        wifi.rs            # ESP32 with WiFi only: joins the network, runs embassy-net
        trunk.rs           # the Nutrient vocabulary + the Trunk handle
        sap.rs             # GENERATED by `bonsai sync` — never edit by hand;
                           # declared inside trunk.rs (`#[path] pub mod sap`)
        pulse.rs           # built-in cycle of life (heartbeat + monitor)
        branches/
          mod.rs           # registry — empty, has the bonsai: markers
```

Boards covered: `pico/{pico,pico-w,pico-2,pico-2w}`,
`esp32/{devkitc-1,xiao}`, and `rpi/{zero-w,zero-2w,pi5}`. The Raspberry Pi templates emit a
Linux userspace application, using Embassy's standard executor and the same
branch and nutrient scaffolds. It has no HAL. Its `.cargo/config.toml` builds
for the Pi, and its runner copies the binary to the Pi over ssh (`BONSAI_PI`)
and runs it there; `cargo local` runs on the host.

## The branch contract

Every branch module exposes a `start()` that spawns its task. The trunk owns
the hardware, so a branch that needs a pin takes it as an argument:

```rust
pub fn start(spawner: &Spawner, trunk: &Trunk /*, led: Output<'static> */) {
    spawner.spawn(run(/* … */)).unwrap();
}

#[embassy_executor::task]
async fn run(/* … */) { loop { /* subsystem logic; await timers/events */ } }
```

`bonsai branch` inserts above two markers in **two files** — keep them intact:

```rust
// src/branches/mod.rs — the registry (starts empty)
// bonsai:mod           <-- new `pub mod <name>;` lines go here
```
```rust
// src/main.rs — the trunk, where branches are started and given hardware
    pulse::start(&spawner, &trunk);   // built-in cycle of life (pulse.rs)
    // bonsai:start      <-- new `branches::<name>::start(&spawner, &trunk);` calls go here
```

`insert_before_marker` in the CLI matches the marker as a whole line, so a doc
comment mentioning `// bonsai:mod` in prose won't be mistaken for it.

The **pulse** (`src/pulse.rs`) is core trunk plumbing, not a branch: a heartbeat
that releases a `Beat` into the sap and a monitor that logs each beat. It's identical on every MCU board (defmt
logging); only the transport differs — Pico sends defmt over RTT (`probe-rs`),
ESP32 over espflash. The rpi boards print to stdout/stderr instead.

**`src/sap.rs` is generated.** The CLI renders it from the template's own
`trunk.rs` + `pulse.rs` + `bonsai.toml` (and `Cargo.toml`, to pick defmt or
stderr for lag reports). After changing any of those in a template, run
`bonsai sync` inside `templates/<mcu>/<board>/`. The
`template_sap_matches_generator` test fails if a board's copy is stale. It
contains no Liquid, so cargo-generate passes it through untouched.

## Variables in a trunk template

Passed by the wizard via `-d`: `mcu`, `chip`, `board`, and `wifi` (true or
false) for MCUs that have it (`has_wifi` in `src/main.rs`; declared as a
`bool` placeholder in the ESP32 templates' `cargo-generate.toml`). With
`wifi = false`, `[conditional.'!wifi']` leaves `src/wifi.rs` out and the
`{% if wifi %}` blocks in `Cargo.toml`, `.cargo/config.toml`, `src/main.rs`
and `README.md` render to nothing, so the tree is the same as without the
option. `regrow` and `update` read the choice back from the tree (an
`esp-radio` dependency means WiFi). Built in by
cargo-generate: `project-name`, `crate_name`. Derived in `pre.rhai`: `target`,
`probe_chip` (Pico) / `target` (ESP32).

## Adding a board or MCU

1. Add it to `boards()` / `MCUS` / `chips()` in `src/main.rs`.
2. Create `templates/<mcu>/<board>/` — copy an existing board's trunk and
   adjust the HAL bits (`Cargo.toml`, `src/main.rs`, `.cargo/config.toml`).
   The `src/branches/`, `src/trunk.rs` and `bonsai.toml` files are portable;
   reuse them as-is, then run `bonsai sync` in the new directory to generate
   its `src/sap.rs`.

## Rendering

Every file passes through [Liquid], so `{{ project-name }}`,
`{% if chip == "rp2350" %}...{% endif %}`, etc. work. The branch scaffold
(`_branch/branch.rs`) is *not* rendered by cargo-generate — the CLI does a
plain `{{branch_name}}` substitution when you run `add branch`.
